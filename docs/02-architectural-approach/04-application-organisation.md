### 2.4 Application Organisation

To avoid confusion with the cFE core and with processor cores, the main groups of flight applications are described as **application suites**.

The proposed organisation contains three principal suites:

1. **Mission and Data-Handling Application Suite**
2. **Subsystem Interface Application Suite**
3. **AOCS and Propulsion Application Suite**

These suites are logical software groupings. They are not separate processor cores.

#### Mission and Data-Handling Application Suite  (the CDH-core)

This suite handles:

- Spacecraft mode management
- Mission scheduling
- Ground-command coordination
- Payload operations
- Payload-data buffering
- File storage
- Downlink queueing
- Software update
- General FDIR coordination

Its main non-critical data path is:

```text
Payload data reception
→ RAM buffering
→ Non-volatile storage
→ File integrity checks
→ Downlink queueing
→ S-band or selected link
```

Payload processing, file access and downlink preparation execute at a lower priority than AOCS and propulsion-related tasks.

#### Subsystem Interface Application Suite (the Driver-core)

This suite manages communication with hardware and COTS subsystems such as:

- Reaction wheels
- IMUs
- Star trackers
- Sun sensors
- Magnetometers
- Magnetorquers
- Propulsion controller
- Power system
- Radios
- Payload electronics

It handles:

- Software Bus subscriptions
- Command encoding
- Telemetry decoding
- Transaction timeouts
- Protocol sequence counters
- Link-level retries
- Data buffering
- Timestamping on reception
- Communication-health monitoring
- Conversion into common internal data types

The Subsystem Interface Applications publish normalised data onto the Software Bus.

For example, the AOCS Application receives a common angular-rate message rather than a vendor-specific IMU packet. If the IMU is replaced, only the interface application and device library need to change, provided they continue publishing the same internal message type.

#### AOCS and Propulsion Application Suite (the Runner-core)

This suite executes the critical control and propulsion-supervision paths.

The AOCS path is:

```text
Sensor acquisition
→ Validation and timestamping
→ State estimation
→ Control
→ Limit and inhibit checks
→ Actuator command
→ Deadline and health monitoring
```

The propulsion-supervision path is:

```text
Operation request
→ Mode and inhibit validation
→ Sequence preparation
→ Propulsion-controller command
→ Execution monitoring
→ Result verification
→ Completion or fault reporting
```

The AOCS Application may execute autogenerated C code produced by Embedded Coder or another model-based development environment.

The autogenerated algorithm code should remain separated from platform-specific software. A manually developed wrapper provides:

- Input conversion
- Output conversion
- Input validity checks
- Output saturation
- Timing measurements
- Model initialisation
- Software Bus interface
- FDIR interface

Protection mechanisms outside the control model remain in manually developed and independently testable software. These mechanisms may include:

- Input-age checks
- Invalid-sensor rejection
- Output saturation
- Actuator inhibits
- Fallback-state selection
- Hard-fault response
